# Delta Lake Incremental Processing — SCD Type 1 & Type 2

## Overview

This project demonstrates incremental data processing on Delta Lake using a real-world dataset, the Sample Superstore retail dataset, which contains 9,994 order-line records spanning 2014 to 2017 across 793 unique customers. Rather than working with a pre-built customer table, a customer dimension is derived directly from the raw order history, and two classic data warehousing patterns are implemented and compared: Slowly Changing Dimension Type 1 (SCD1) and Slowly Changing Dimension Type 2 (SCD2). The entire pipeline runs on Delta Lake, using its transaction log and native `MERGE` support to apply an incoming batch of changes to an existing table safely and atomically.

## Some theory: why incremental processing and SCDs matter

In most real data systems, data does not arrive once and stay static. Customers place new orders, change addresses, and update their spending behavior continuously, and a data pipeline has to decide, every time new data shows up, how to reconcile it with what is already stored. Reloading an entire table from scratch on every run is wasteful and does not scale, so instead pipelines process only the new or changed records since the last run. This is incremental processing, and the mechanism that applies those changes to a target table is typically a `MERGE` (also called an upsert), which in a single atomic operation updates rows that already exist and inserts rows that are new.

The question incremental processing does not answer on its own is what happens to the old value when a record changes. This is where Slowly Changing Dimensions come in, a concept from data warehousing that describes different strategies for handling attribute changes over time. SCD Type 1 is the simplest: when a value changes, the old value is simply overwritten. This keeps the table small and the logic simple, but it means history is lost forever; if a customer's spend or address changes, there is no way to know what it used to be. SCD Type 2 takes the opposite approach: instead of overwriting, the old row is marked as no longer current (typically with an `is_current` flag and an `effective_end_date`) and a brand new row is inserted representing the new state, marked as current. This preserves the full history of every change, at the cost of a growing table and more complex merge logic, since a single `MERGE` statement cannot both close out an old row and insert a new one for the same key in one pass; it requires two coordinated steps, an expire step and an insert step.

In this project, the dataset itself was chosen to make both patterns concrete rather than abstract. Three fields are treated as attributes that can change over time for a given customer: `segment`, which in this data happens to be genuinely stable and never changes for any customer, included mainly for completeness; `city`, `state`, and `region`, which represent the shipping destination of a customer's most recent order and are treated as a proxy for their current known location, since these do change frequently as customers ship to different places; and `total_spent`, which is calculated as the customer's cumulative sales as of a given order, meaning it grows every single time they place a new order. This last field in particular guarantees that almost every returning customer in an incremental batch will register as "changed," which mirrors how, in a real system, an ever-growing metric like lifetime spend is one of the most common and reliable triggers for SCD2 versioning.

## How the incremental batch was constructed

Rather than fabricating a synthetic set of "before" and "after" values, the incremental batch in this project was constructed chronologically, which is closer to how incremental data actually arises in production. The full set of orders was sorted by date, and the oldest 85 percent were treated as the baseline dataset already loaded into the system, while the newest 15 percent were treated as the incoming batch representing activity since the last load. Within that incoming window, each customer's most recent snapshot was kept, since a real incremental extract typically reflects the latest known state rather than every intermediate value. This produced a master baseline of 8,489 raw rows collapsing to 789 unique customers, and an incremental batch of 494 rows, of which 490 represented updates to existing customers and 4 represented entirely new customers who had never ordered before.

One further detail is worth being transparent about: the real Superstore dataset contains no missing values at all, but the cleaning step of this pipeline is meant to demonstrate how nulls and duplicates are typically handled. To make that step meaningful, a small number of nulls, roughly 1.5 percent of `segment` values and 1 percent of `city` values, were deliberately and randomly introduced into the master baseline only. Every other value in the dataset is real, unmodified Superstore data.

## Pipeline stages

The notebook proceeds through six stages that mirror a typical batch ETL job. First, the raw data is loaded and a customer dimension is derived from it, including the cumulative spend calculation. Second, that raw extract is cleaned: duplicate customer records are collapsed down to each customer's most recent snapshot, and the small number of injected nulls are filled in. Third, the incremental batch described above is prepared. Fourth, that batch is applied to the target table in two parallel ways, once using the SCD1 overwrite pattern and once using the SCD2 expire-and-insert pattern, so the two approaches can be directly compared on identical input data. Fifth, the results are validated: row counts are checked against what should mathematically be expected, duplicate keys are checked for, and a specific updated customer is spot-checked to confirm their SCD1 record shows only the latest values while their SCD2 record correctly shows two versions with exactly one marked current. Sixth and finally, both resulting tables are displayed in full along with a summary of the run.

## Results

Running this pipeline against the described dataset produced an SCD1 table that grew from 789 rows to 793 rows, since the 490 updates simply overwrote existing rows in place while only the 4 genuinely new customers added new rows, and this table shows no duplicate keys at any point. The SCD2 table, by contrast, grew from 789 rows to 1,283 rows, made up of 793 current rows plus 490 historical rows representing the prior version of every customer who had a tracked attribute change. Every validation check passed. The practical difference between the two tables is easiest to see by picking any single updated customer: in the SCD1 table, that customer has exactly one row showing their latest city, spend, and other attributes, with no trace of what those values used to be; in the SCD2 table, that same customer has two rows, one with `is_current` set to false and an `effective_end_date` populated, representing their old state, and one with `is_current` set to true and no end date, representing their current state. Both are correct outputs, but they answer different questions: SCD1 answers "what does this record look like right now," while SCD2 answers "what did this record look like at any point in time."

## Environment and how to run it

This project was built and run on Databricks Free Edition using serverless compute and Unity Catalog, with the raw CSV uploaded directly as a catalog table rather than a file path, since Free Edition disables the legacy DBFS root storage that older Databricks tutorials assume is available. Output Delta tables are written to a Unity Catalog Volume rather than DBFS for the same reason. Serverless compute also does not support `PERSIST TABLE`, so the pipeline deliberately avoids `.cache()` or `.persist()` calls anywhere, relying on Spark to simply recompute intermediate results as needed, which is entirely reasonable at this data volume of under ten thousand rows. A parallel, offline version of the same logic also exists using the `deltalake` Python package (delta-rs) with pandas instead of PySpark, useful for running the exact same pipeline locally in a plain Jupyter notebook without needing a Spark cluster at all, which is how the results above were independently verified before being run on Databricks.

## Project structure

The repository is organized with the raw `Sample_-_Superstore.csv` file sitting alone in a `data` folder, since it is the only input the pipeline needs; a `databricks` folder containing the notebook exported from Databricks as a source file; a `notebooks` folder containing the equivalent notebook for local, offline execution; a `screenshots` folder with six subfolders, one for each pipeline stage described above, containing evidence that each stage ran correctly; and an optional `report` folder with a short written summary suitable for submission alongside the code itself.
